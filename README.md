# Patroni Playground

Цель: разобраться, как PostgreSQL реплицирует данные и как Patroni управляет
кластером при отказах.

## Что мы строим

```text
                         HAProxy
                     localhost:55432 ──────► primary: чтение и запись
                     localhost:55433 ──────► replicas: только чтение
                             │
                ┌────────────┼────────────┐
                ▼            ▼            ▼
               pg1          pg2          pg3
           PostgreSQL   PostgreSQL   PostgreSQL
            + Patroni    + Patroni    + Patroni
                └────────────┼────────────┘
                             ▼
                    etcd1, etcd2, etcd3
                 выбор лидера и конфигурация
```

- **PostgreSQL** хранит данные. Primary принимает запись; replicas получают
  и воспроизводят WAL — журнал изменений. Это streaming replication.

- **Patroni** работает рядом с каждым PostgreSQL, управляет его запуском,
  остановкой и сменой роли. `pg1` — имя узла, его роль может меняться.

- **etcd** — распределённое хранилище координации, DCS. Здесь хранится аренда
  лидерства и общая конфигурация Patroni. Для кворума нужны два из трёх etcd.
  Строки таблиц хранятся в PostgreSQL.

- **HAProxy** проверяет REST API Patroni: `/primary` для записи, `/replica`
  для чтения. Новое соединение направляется на подходящий узел.

Версии: PostgreSQL 17.11, Patroni 4.1.5, etcd 3.6.5, HAProxy 3.2.
Образ PostgreSQL закреплён digest; etcd и HAProxy используют теги,
транзитивные Python-зависимости.

## Как читать команды

Команды `make sql`, `make ctl` и `make status` — имена целей нашего `Makefile`.
Они запускают нужные программы с настройками стенда.

| Команда | Что означает и что запускает |
| --- | --- |
| `make sql` | SQL — язык запросов к БД. Команда открывает клиент `psql` через HAProxy к текущему primary |
| `make ctl ARGS="..."` | `ctl` — сокращение от control. Запускает `patronictl`, программу управления кластером Patroni |
| `make status` | Запускает `patronictl list` и показывает роли и состояние PostgreSQL-узлов |

`NODE` выбирает **контейнер для запуска клиента**; по умолчанию это `pg1`.
Можно выбрать любой работающий PostgreSQL-контейнер стенда. Его роль может быть
как лидером, так и репликой: `NODE` не назначает лидера и не выбирает целевую БД.

Например:

```bash
make ctl NODE=pg2 ARGS="show-config"
```

разворачивается в:

```bash
docker compose exec pg2 patronictl -c /etc/patroni.yaml show-config
```

`ARGS` передаёт действие и его параметры программе `patronictl`.
В этом примере она читает общую конфигурацию из DCS; менять конфигурацию через
`edit-config` тоже можно с узла, который работает репликой.

Для SQL:

```bash
make sql NODE=pg2
make sql NODE=pg2 PORT=5001
```

В обоих случаях `psql` запускается внутри `pg2`. По умолчанию используется
`PORT=5000` — порт HAProxy внутри Docker, ведущий к primary. `PORT=5001` ведёт
к репликам. Эти значения отличаются от опубликованных портов хоста
`55432` и `55433`. Выход из `psql`: `\q`.

## Запуск

Docker Engine, Docker Compose **2.24.4+**, Python 3 и Make. Все семь контейнеров
работают на одной машине: моделируем отказы процессов, а отказ хоста остановит весь стенд.

Открой папку проекта:

```bash
cd /home/leprecha/patroni-playground
make up
make status
```

В исходном асинхронном режиме ожидается один `Leader` и две `Replica`
в состоянии `streaming`. После включения синхронного режима одна реплика
будет обозначена как `Sync Standby`.
Первым лидером может стать любой узел. Сборка в первый раз занимает несколько минут.
Если запуск завершился ошибкой: `docker compose logs --tail=80`.

`make setup` автоматически создаёт `.env` с двумя случайными паролями и правами
`0600`. Повторный запуск сохраняет файл. Он исключён из Git. Сохраняй `.env`,
пока сохраняешь данные кластера: изменение файла само по себе не меняет пароли в БД.

Это локальный стенд: внешние порты привязаны к `127.0.0.1`, TLS
и watchdog не настроены, административный REST API без пароля.
Репликация не заменяет резервные копии: `DELETE` тоже попадёт на реплики.

## 1. Находим primary и создаём данные

```bash
make sql
```

Откроется `psql`, подключённый через HAProxy к primary. Выполни:

```sql
SELECT inet_server_addr(), pg_is_in_recovery();

CREATE TABLE notes (
    id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    body text NOT NULL,
    created_at timestamptz NOT NULL DEFAULT now()
);

INSERT INTO notes (body) VALUES ('Привет, Patroni!');
SELECT * FROM notes;
```

У primary `pg_is_in_recovery()` возвращает `false`. Запомни IP сервера:
позже он поможет заметить переключение. Выход из `psql`: `\q`.

HAProxy допускает до часа бездействия SQL-соединения (`timeout client` и
`timeout server` в `haproxy.cfg`). После более долгой паузы соединение может
закрыться; `Attempting reset: Succeeded` означает, что `psql` подключился заново.
Это новый сеанс: временные таблицы и настройки предыдущего сеанса не сохраняются.
Открытая транзакция, до COMMIT которой дело не дошло, откатывается.
Если связь потеряна во время самого COMMIT, его результат может быть
неизвестен клиенту; перед повтором операции проверь данные.

## 2. Читаем с реплики

```bash
make sql PORT=5001
```

`5001` — порт HAProxy внутри Docker. Выполни:

```sql
SELECT inet_server_addr(), pg_is_in_recovery();
SELECT * FROM notes;
INSERT INTO notes (body) VALUES ('Запись с реплики?');
```

Ожидай `true`, строку из первого упражнения и ошибку `read-only transaction`
при вставке. В исходной конфигурации репликация асинхронная, поэтому данные
могут появиться с небольшой задержкой.
HAProxy выбирает узел при установлении соединения. Один сеанс `psql` остаётся
на одной реплике; переподключение может привести на другую.

## 3. Смотрим репликацию

Подключись к primary через `make sql`:

```sql
SELECT application_name, state, sync_state,
       sent_lsn, write_lsn, flush_lsn, replay_lsn
FROM pg_stat_replication;
```

В исходном асинхронном режиме ожидай две строки: `state = streaming`, `sync_state = async`.
LSN — позиция в WAL. Эти столбцы показывают этапы доставки:
отправка, запись, сброс на диск и воспроизведение на реплике.

На реплике через `make sql PORT=5001`:

```sql
SELECT pg_last_wal_receive_lsn(), pg_last_wal_replay_lsn();
```

Добавь несколько строк на primary и повтори запросы. После доставки изменений
позиции приёма и воспроизведения на реплике обычно совпадают.

## 4. Плановое переключение — switchover

```bash
make status
make ctl ARGS="switchover"
```

В диалоге выбери текущего лидера, другую здоровую реплику и немедленное
переключение, затем подтверди действие. `make status` покажет нового `Leader`.
Бывший лидер должен вернуться как `Replica` в состоянии `streaming`.

Открытое соединение `psql` при смене роли может оборваться. Подключись снова:

```bash
make sql
```

```sql
SELECT inet_server_addr(), pg_is_in_recovery();
INSERT INTO notes (body) VALUES ('После switchover');
SELECT * FROM notes;
```

Адрес подключения остался прежним; сервер за HAProxy изменился.
Приложению нужно уметь переподключаться. Если связь оборвалась во время `COMMIT`,
результат транзакции может быть неизвестен клиенту: перед повтором записи
проверь результат или используй уникальный ключ операции.

## 5. Аварийное переключение — failover

Выйди из `psql`. По `make status` найди текущего лидера. Ниже пример
для лидера **pg1**; замени имя, если лидер другой:

```bash
docker compose kill -s SIGKILL pg1
make status NODE=pg2
```

Это завершение контейнера без корректной остановки PostgreSQL.
Patroni на оставшихся узлах должен выбрать нового лидера. Повторяй просмотр
статуса: переключение обычно занимает десятки секунд. `ttl = 20`, `loop_wait = 5`
и `retry_timeout = 5` задают интервалы координации; фактическое время зависит
от обнаружения отказа, выборов и запуска PostgreSQL.

```bash
make sql NODE=pg2
```

```sql
INSERT INTO notes (body) VALUES ('После аварии');
SELECT * FROM notes;
```

`NODE` выбирает контейнер, в котором запускается клиент `psql` или `patronictl`.
Сам `psql` по-прежнему идёт к primary через HAProxy. Если остановлен `pg2`,
используй `NODE=pg1` или `NODE=pg3`.

**Почему возможна потеря данных:** в async-режиме primary подтверждает транзакцию,
не дожидаясь её доставки на реплику. Последние подтверждённые записи могут
отсутствовать на новом primary. `maximum_lag_on_failover = 1048576` ограничивает
отставание кандидата, но не гарантирует RPO в 1 МиБ: позиция лидера измеряется
периодически.

## 6. Возвращаем бывшего лидера

Для остановленного в прошлом `pg1`:

```bash
docker compose start pg1
make status NODE=pg2
```

Ожидай, что `pg1` станет репликой и получит строку «После аварии».
При расхождении истории WAL Patroni может использовать `pg_rewind`;
для этого включены `use_pg_rewind` и checksums при `initdb`.
Посмотри решение Patroni в `docker compose logs --tail=100 pg1`.
Если для возврата недостаёт WAL, ручная переинициализация — следующий шаг.

## 7. Зачем etcd нужен кворум

Начинай со всех работающих узлов:

```bash
docker compose stop etcd3
make status
```

Два etcd из трёх сохраняют кворум, кластер продолжает работать. Теперь:

```bash
docker compose stop etcd2
```

Кворум потерян. В этом стенде `failsafe_mode = false`: после неудачных попыток
продлить аренду лидер должен отказаться от роли primary. Подожди около 30 секунд:

```bash
docker compose logs --tail=40 pg1 pg2 pg3
curl -i http://127.0.0.1:8001/primary
curl -i http://127.0.0.1:8002/primary
curl -i http://127.0.0.1:8003/primary
```

Ожидай `503` у всех трёх. Запись через HAProxy станет недоступна.
`patronictl list` тоже может завершиться ошибкой: для него нужен DCS.
Работающие реплики PostgreSQL не заменяют потерянный кворум etcd.

Восстанови кворум и дождись возврата лидера:

```bash
docker compose start etcd2 etcd3
make status
make sql
```

## 8. Синхронная репликация

Проверяем, чего именно ждёт подтверждение транзакции и как доступность
записи зависит от работающих реплик.
Динамическая конфигурация сохраняется в etcd между остановками стенда.

### Что означает synchronous_commit

`synchronous_commit` — настройка PostgreSQL: какие действия с WAL должны
завершиться до успешного ответа клиенту на `COMMIT`. Отдельный `INSERT`
без `BEGIN` тоже выполняется в собственной транзакции.

| Настройки | Что требуется для подтверждения COMMIT |
| --- | --- |
| `synchronous_commit=off` | Сброс WAL на диск не ожидается; последние подтверждённые транзакции могут потеряться при аварии PostgreSQL |
| `synchronous_commit=on`, синхронные реплики не назначены | WAL сохранён на диске лидера |
| `synchronous_commit=on`, назначена одна синхронная реплика | WAL сохранён на диске лидера и этой реплики |

Реплика с `sync_state=async` тоже получает WAL, но её подтверждение не требуется
для успешного `COMMIT`. `Sync Standby` означает «синхронная реплика»;
подтверждения ждёт лидер. Сохранение WAL на реплике ещё не означает, что он уже
воспроизведён и изменения доступны для чтения на ней.

### Включаем одну синхронную реплику

Начинай с трёх здоровых PostgreSQL-узлов. В примере лидер — `pg2`,
реплики — `pg1` и `pg3`. Перед каждой остановкой сверяй роли через `make status`:
если имена отличаются, подставляй фактические имена узлов.

```bash
make status NODE=pg2
make ctl NODE=pg2 ARGS="edit-config --set synchronous_mode=true --set synchronous_node_count=1 --set synchronous_mode_strict=true"
```

Подтверди изменения. Эти настройки меняются через DCS; правка `bootstrap.dcs`
в существующем кластере их не изменит.

- `synchronous_mode=true`: Patroni назначает синхронные реплики и ограничивает
  круг узлов, которым разрешено автоматическое повышение.
- `synchronous_node_count=1`: достаточно подтверждения одной синхронной реплики.
- `synchronous_mode_strict=true`: при отсутствии подходящих реплик Patroni
  сохраняет требование синхронного подтверждения; `COMMIT` будет ждать.

Через несколько секунд:

```bash
make status NODE=pg2
make sql NODE=pg2
```

```sql
SHOW synchronous_commit;
SHOW synchronous_standby_names;
SELECT application_name, state, sync_state
FROM pg_stat_replication
ORDER BY application_name;
```

Ожидай `synchronous_commit=on`, непустой список синхронных реплик и одну строку
с `sync_state=sync`. В следующих примерах первоначально выбран `pg3`, а `pg1`
остаётся асинхронной репликой. В `patronictl list` выбранный узел отображается
как `Sync Standby`.

### Теряем синхронную реплику

Выйди из `psql` через `\q`. Останови выбранную синхронную реплику:

```bash
docker compose kill -s SIGKILL pg3
make status NODE=pg2
```

Дождись, пока `pg1` станет `Sync Standby`. Лидер остаётся `pg2`, timeline
не меняется: здесь нет повышения нового primary. Статус остановленного `pg3`
может некоторое время оставаться в DCS; фактическое состояние контейнеров
видно в `docker compose ps -a`.

```bash
make sql NODE=pg2
```

```sql
SHOW synchronous_standby_names;
INSERT INTO notes (body)
VALUES ('Запись после замены синхронной реплики') RETURNING *;
```

Ожидай `pg1` в настройке и успешную вставку. `pg3` пока остаётся остановленным.

### Теряем все реплики в строгом режиме

Оставь первый терминал с `psql`, подключённым к лидеру. Во втором терминале
из папки проекта останови оставшуюся реплику:

```bash
docker compose kill -s SIGKILL pg1
```

В первом терминале:

```sql
BEGIN;
INSERT INTO notes (body) VALUES ('Проверка ожидания синхронной реплики');
COMMIT;
```

`INSERT` внутри транзакции выполнится, а `COMMIT` будет ждать подтверждения
синхронной реплики. Лидер и etcd работают; причина ожидания — отсутствие
подтверждения WAL от реплики.

Во втором терминале верни `pg1`:

```bash
docker compose start pg1
```

После её присоединения ожидающий `COMMIT` должен завершиться сам.
Для этого упражнения возвращаем реплику, сохраняя ожидающий сеанс.
Отмена ожидания или потеря соединения во время `COMMIT` требует проверки
результата транзакции: отсутствие успешного ответа не доказывает откат.

### Выключаем строгость и сравниваем поведение

Сейчас `pg2` — лидер, `pg1` — синхронная реплика, `pg3` ещё остановлен.
Во втором терминале:

```bash
make ctl NODE=pg2 ARGS="edit-config --set synchronous_mode_strict=false"
docker compose kill -s SIGKILL pg1
```

Подтверди изменение конфигурации. В `psql` на лидере:

```sql
INSERT INTO notes (body)
VALUES ('Запись без реплик в нестрогом режиме') RETURNING *;
SHOW synchronous_standby_names;
```

После возможной короткой паузы Patroni отключит ожидание реплик, запись
завершится, а `synchronous_standby_names` станет пустым. Подтверждённые в этом
состоянии изменения могут находиться только на диске лидера.

Верни обе реплики и дождись их присоединения:

```bash
docker compose start pg1 pg3
make status NODE=pg2
```

`synchronous_mode` остаётся включённым. Когда подходящая реплика снова появилась,
Patroni назначит её синхронной, и `COMMIT` опять будет ждать её подтверждения.

| Все подходящие реплики недоступны | Поведение записи на работающем лидере |
| --- | --- |
| `synchronous_mode_strict=true` | `COMMIT` ждёт реплику |
| `synchronous_mode_strict=false` | После реакции Patroni запись подтверждается только лидером |

## 9. Потеря лидера и синхронной реплики

`synchronous_mode_strict=false` разрешает живому лидеру работать без реплик.
При `synchronous_mode=true` это не даёт асинхронной реплике права автоматически
стать лидером после потери остальных узлов.

### Оставляем только асинхронную реплику

Проверь роли и конфигурацию:

```bash
make status NODE=pg2
make ctl NODE=pg2 ARGS="show-config"
```

Для примера нужны `pg2 = Leader`, `pg3 = Sync Standby`, `pg1 = Replica`,
`synchronous_mode=true`, `synchronous_node_count=1`. Если назначена другая
синхронная реплика, замени имена в командах и выбери оставшийся узел для `NODE`.
Все etcd остаются работать. Выйди из `psql` через `\q`.

Выполни блок целиком, без паузы: сначала останавливается лидер, затем синхронная
реплика. Так лидер не успеет назначить оставшийся узел синхронным до своего отказа.

```bash
docker compose kill -s SIGKILL pg2 &&
docker compose kill -s SIGKILL pg3
```

Примерно через 30 секунд:

```bash
make status NODE=pg1
docker compose exec pg1 psql -U postgres -d postgres \
  -c 'SELECT pg_is_in_recovery();'
```

Ожидай `pg1 = Replica`, состояние `running`, `pg_is_in_recovery()=true`
и отсутствие лидера. Даже нулевой показанный `Lag` не даёт этому узлу права
на автоматическое повышение в данном режиме. Уже полученный WAL можно
воспроизвести, но недоставленную часть в этом стенде получать больше неоткуда.

### Возвращаем допустимого кандидата

Верни только бывшую синхронную реплику:

```bash
docker compose start pg3
make status NODE=pg1
```

При работающем DCS и успешных проверках Patroni повысит `pg3` автоматически.
Появится новая timeline, `pg1` подключится к новому лидеру и сможет стать
синхронной репликой.

```bash
make sql NODE=pg1
```

```sql
SELECT inet_server_addr(), pg_is_in_recovery();
INSERT INTO notes (body) VALUES ('Запись после возвращения pg3') RETURNING *;
\q
```

После успешной записи верни бывшего лидера:

```bash
docker compose start pg2
make status NODE=pg1
docker compose exec pg2 psql -U postgres -d postgres \
  -c "SELECT pg_is_in_recovery(); SELECT id, body FROM notes WHERE body = 'Запись после возвращения pg3';"
```

Ожидай, что `pg2` вернулся репликой и получил новую строку. Это автоматический
выбор лидера после возвращения подходящего узла, а затем присоединение старого
primary к новой истории.

### Где данные, пока нет лидера

Без лидера этот кластер не подтверждает новые операции записи. Приложение
получает ошибку подключения либо ждёт до таймаута. Patroni не сохраняет
неуспешные SQL-запросы в очередь. Для отложенной обработки нужна отдельная
надёжная очередь и соответствующая логика приложения.

Если запись была подтверждена до отказа лидера, её местонахождение зависит
от режима в тот момент. В нестрогом режиме без реплик она могла остаться только
на диске лидера. На границе сбоя результат `COMMIT` может быть неизвестен клиенту;
при повторе операции нужен способ избежать дубликатов.

Patroni управляет PostgreSQL, но для возврата самого процесса Patroni, контейнера
или машины нужна работающая система запуска. Если безопасного кандидата вернуть
не удалось, оператор исследует состояние узлов и источники восстановления.
Принудительное повышение асинхронной реплики — отдельное решение с возможной
потерей данных, которое в этом упражнении не выполняется.

## 10. Пересоздание реплики после потери WAL — reinit

При обычном возвращении реплика дочитывает WAL. Если нужные сегменты уже удалены
и доступного архива нет, цепочку воспроизведения продолжить нельзя. Тогда нужна
новая базовая копия данных. `patronictl reinit` пересоздаёт PostgreSQL на выбранной
реплике и снова подключает её к потоку WAL.

**Reinit заменяет весь каталог данных целевой реплики.** Перед подтверждением
проверь имя узла и источник копии. В этом упражнении пересоздаём только `pg2`;
лидер `pg3` и синхронная реплика `pg1` продолжают работать.

### Проверяем роли и удержание WAL

Для следующих команд исходное состояние такое:

| Узел | Роль |
| --- | --- |
| `pg3` | Leader |
| `pg1` | Sync Standby, streaming |
| `pg2` | Асинхронная Replica, streaming — цель упражнения |

```bash
make status NODE=pg3
make sql NODE=pg3
```

```sql
SHOW wal_keep_size;
SHOW max_slot_wal_keep_size;
SHOW archive_mode;

SELECT application_name, state, sync_state
FROM pg_stat_replication ORDER BY application_name;

SELECT slot_name, active, restart_lsn, wal_status
FROM pg_replication_slots ORDER BY slot_name;
\q
```

Ожидай `128MB`, `256MB`, `off`, две streaming-реплики, синхронную `pg1`
и активные физические slots `pg1` и `pg2`. Запиши исходные значения хранения WAL:
в конце их нужно вернуть. Если роли отличаются, сначала выбери фактическую
асинхронную реплику и согласуй имена во всех командах этой главы.

`wal_keep_size` сохраняет минимальный объём старых сегментов. Replication slot
удерживает WAL для своей реплики, но `max_slot_wal_keep_size` ограничивает это
удержание при checkpoint. Поэтому одной остановки реплики и пары вставок
недостаточно, чтобы воспроизвести потерю WAL.

### Уменьшаем удержание и останавливаем целевую реплику

Для короткого локального упражнения временно уменьши удержание WAL:

```bash
make ctl NODE=pg3 ARGS="edit-config --pg wal_keep_size=16MB --pg max_slot_wal_keep_size=16MB"
```

Подтверди изменения и через несколько секунд проверь их на лидере:

```bash
docker compose exec pg3 psql -U postgres -d postgres \
  -c 'SHOW wal_keep_size;' -c 'SHOW max_slot_wal_keep_size;'
```

Ожидай `16MB` для обоих параметров. Установленный Patroni отклоняет
`wal_keep_size=0` и оставляет значение по умолчанию, поэтому здесь используем
поддерживаемые `16MB`. Теперь останови только асинхронную реплику:

```bash
docker compose stop pg2
```

### Создаём реальный разрыв WAL

```bash
make sql NODE=pg3
```

```sql
CREATE TABLE lab_wal_pressure (
    id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY
);

DO $$
BEGIN
    FOR i IN 1..12 LOOP
        INSERT INTO lab_wal_pressure DEFAULT VALUES;
        PERFORM pg_switch_wal();
    END LOOP;
END;
$$;

CHECKPOINT;

SELECT slot_name, active, restart_lsn, wal_status
FROM pg_replication_slots ORDER BY slot_name;

INSERT INTO notes (body)
VALUES ('Запись во время отсутствия pg2') RETURNING *;
\q
```

Вставки создают WAL, а `pg_switch_wal()` переключает сегменты. Двенадцать
переключений продвигают WAL примерно на 192 МиБ при стандартном сегменте 16 МиБ,
хотя в таблице всего двенадцать строк. Checkpoint позволяет применить лимит slot
и убрать старые сегменты. Сам по себе `pg_switch_wal()` без новой WAL-активности
не обязан каждый раз создавать следующий сегмент.

У отставшего slot может появиться `wal_status=lost`. Patroni также может удалить
и пересоздать непригодный slot.

### Видим, почему обычного start недостаточно

```bash
docker compose start pg2
make status NODE=pg3
docker compose logs --tail=100 pg2
```

Ожидай в логах `requested WAL segment ... has already been removed`.
`pg2` не сможет вернуться к `streaming`. Лидер и здоровая синхронная реплика
должны продолжать работу. Если ошибки нет и `pg2` уже догнал лидера, разрыв WAL
не воспроизведён: сначала проверь значения хранения WAL и выполнение checkpoint.

### Пересоздаём только pg2

Процесс Patroni на `pg2` должен работать и отвечать на REST API, даже если
его PostgreSQL не может продолжить streaming. Имя кластера в команде — текущее
значение `scope`; в этом проекте оно содержит пробелы и поэтому взято в кавычки.

```bash
make ctl NODE=pg3 ARGS="reinit 'how to drive ;)' pg2 --from-leader --wait"
```

Перед подтверждением проверь, что указан именно `pg2` в роли реплики.
Patroni остановит её PostgreSQL, заменит каталог данных базовой копией и запустит
реплику заново. `--from-leader` выбирает лидера источником `pg_basebackup`,
`--wait` ожидает завершения пересоздания. Затем дождись `streaming`:

```bash
make status NODE=pg3
docker compose exec pg2 psql -U postgres -d postgres \
  -c 'SELECT pg_is_in_recovery();' \
  -c "SELECT id, body FROM notes WHERE body = 'Запись во время отсутствия pg2';" \
  -c 'SELECT count(*) FROM lab_wal_pressure;'
```

Ожидай `true`, новую строку из `notes` и `12` строк в таблице упражнения.
Лидер и timeline при reinit реплики не должны меняться.

### Возвращаем удержание WAL и проверяем дальнейшую репликацию

Верни записанные исходные значения; для исходной конфигурации стенда:

```bash
make ctl NODE=pg3 ARGS="edit-config --pg wal_keep_size=128MB --pg max_slot_wal_keep_size=256MB"
make sql NODE=pg3
```

```sql
SHOW wal_keep_size;
SHOW max_slot_wal_keep_size;

INSERT INTO notes (body) VALUES ('После reinit pg2') RETURNING *;
DROP TABLE lab_wal_pressure;
\q
```

Если `SHOW` ещё показывает временные значения, подожди применения конфигурации
и повтори проверку. Затем на пересозданной реплике:

```bash
docker compose exec pg2 psql -U postgres -d postgres \
  -c "SELECT id, body FROM notes WHERE body = 'После reinit pg2';"
make status NODE=pg3
```

Упражнение завершено, когда три узла работают, обе реплики находятся в
`streaming`, новая запись дошла до `pg2`, а лимиты хранения WAL восстановлены.

## 11. Измеряем отказ под непрерывной записью

До этого проверяли отдельные вставки. Теперь клиент будет постоянно писать
через HAProxy, сохранять журнал результатов на хосте и сравнивать подтверждённые
операции с данными нового лидера.

### Что именно измеряется

Нужны Python 3 и `psql` на хосте. Python использует стандартную библиотеку;
драйвер PostgreSQL для Python устанавливать не требуется.

```bash
psql --version
python3 workload.py write --help
```

Клиент работает на хосте и продолжает работу при остановке контейнера лидера.
Пароль берётся из локального `.env` и передаётся `psql` через окружение.
Каждая попытка открывает новое соединение к `127.0.0.1:55432`.
В соединении явно задан `synchronous_commit=on`; режим Patroni определяет,
нужно ли при этом ожидать реплику. Проверяется подключение к узлу, допускающему
запись, и используются ограниченные таймауты подключения и запроса.

Данные пишутся в отдельную таблицу `public.lab_workload`. У каждого запуска
свой `run_id`, а у каждой попытки — свой `seq`. Существующие строки предыдущих
запусков сохраняются. `notes` используется предыдущими упражнениями.

Журнал `.local/workload/<run_id>.jsonl` находится вне volumes PostgreSQL:

1. Перед отправкой SQL клиент сохраняет событие `attempt`.
2. После успешного завершения `psql` и получения ожидаемого идентификатора
   сохраняет `ack` — клиент получил подтверждение завершения транзакции.
3. При ошибке или таймауте сохраняет `unconfirmed`: успешного подтверждения нет,
   но запись могла успеть сохраниться.

События сбрасываются на диск хоста. Это защищает журнал от отказа контейнера БД;
отказ самого хоста здесь не моделируется. Неопределённые операции в этом
упражнении автоматически не повторяются: следующая попытка получает новый `seq`.
Повтор с тем же идентификатором разберём в блоке о поведении приложения.

### Запускаем без отказа

Сначала проверь здоровую конфигурацию из трёх узлов и восстановленные после
главы 10 значения `wal_keep_size=128MB`, `max_slot_wal_keep_size=256MB`.

```bash
make status
make load DURATION=10
make load-report
```

Клиент показывает путь журнала и счётчики `attempts`, `ACK`, `no_ACK`.
`DURATION` задаёт длительность запуска в секундах. `INTERVAL` — пауза между
попытками, по умолчанию `0.1` секунды. Время открытия соединения и выполнения
SQL добавляется к этой паузе, поэтому это не обещание ровно десяти записей в секунду.

`make load-report` выбирает последний журнал, обращается к текущему primary
через HAProxy и сохраняет JSON в `.local/workload/<run_id>.report.json`.
Для конкретного запуска укажи путь, напечатанный клиентом:

```bash
make load-report JOURNAL='.local/workload/<run_id>.jsonl'
```

`<run_id>` в примере нужно заменить фактическим UUID. Журналы и отчёты исключены
из Git через `.local/`. Отчёт строится после завершения клиента; Ctrl+C
останавливает его с записью завершающего события. Незавершённый журнал после
аварийного завершения клиента отчёт отклоняет, а не считает успешным измерением.

Без отказов ожидай `acknowledged > 0`, `unconfirmed = 0`,
`confirmed_missing_count = 0`, пустой `error_windows`.

### Измеряем отказ лидера в синхронном режиме

В примере исходный лидер — `pg3`, одна из реплик — `Sync Standby`.
Перед остановкой проверь фактические роли и согласуй имена в командах.

В первом терминале:

```bash
make ctl NODE=pg3 ARGS="edit-config --set synchronous_mode=true --set synchronous_mode_strict=true --set synchronous_node_count=1"
make status NODE=pg3
make load DURATION=60
```

Подтверди изменения и дождись назначения синхронной реплики перед запуском
нагрузки. Когда клиент уже показал хотя бы десять `ACK`, во втором терминале:

```bash
docker compose kill -s SIGKILL pg3
make status NODE=pg1
```

Повторяй просмотр статуса до появления нового лидера. Клиент в первом терминале
продолжает попытки, фиксирует ошибки и затем снова получает подтверждения.
После возобновления успешных операций подожди несколько секунд и останови
клиент через Ctrl+C либо дождись окончания 60 секунд.

Построй отчёт **до возвращения старого лидера**:

```bash
make load-report
```

При отказе только лидера и доступной синхронной реплике ожидаем
`confirmed_missing_count = 0`. Обычно появятся `unconfirmed` и окно ошибок с
`recovered=true`. Число ошибок зависит от таймаутов и частоты попыток.
Результат относится к этому конкретному прогону и настройкам.

После сохранения отчёта верни остановленный узел и дождись streaming:

```bash
docker compose start pg3
make status NODE=pg1
```

### Сравниваем с асинхронным режимом

Начинай снова с трёх здоровых узлов. В следующем примере после предыдущего
отказа лидер — `pg1`; если роль досталась другому узлу, замени имена.

```bash
make ctl NODE=pg1 ARGS="edit-config --set synchronous_mode=false --set synchronous_mode_strict=false"
make sql NODE=pg1
```

```sql
SHOW synchronous_standby_names;
SELECT application_name, sync_state FROM pg_stat_replication;
\q
```

Дождись пустого `synchronous_standby_names` и двух `async`-реплик.
В первом терминале:

```bash
make load DURATION=60
```

После появления хотя бы десяти подтверждений во втором терминале:

```bash
docker compose kill -s SIGKILL pg1
make status NODE=pg2
```

После выбора нового лидера и возврата успешных записей останови клиент
через Ctrl+C. Сохрани отчёт до возвращения старого primary:

```bash
make load-report
```

В async возможны отсутствующие подтверждённые операции. На быстрой локальной
репликации результат часто тоже равен нулю: это показывает, что потери не
наблюдались в данном опыте, а не гарантирует их невозможность.

Верни узел и синхронный режим, использованный перед этой главой:

```bash
docker compose start pg1
make status NODE=pg2
make ctl NODE=pg2 ARGS="edit-config --set synchronous_mode=true --set synchronous_mode_strict=false --set synchronous_node_count=1"
```

Дождись трёх работающих узлов, двух streaming-реплик и одного `Sync Standby`.
Журналы обоих прогонов имеют разные UUID и сохраняются для сравнения.

### Читаем отчёт правильно

| Поле | Значение |
| --- | --- |
| `acknowledged` | Клиент получил подтверждение успешного завершения операции |
| `confirmed_missing_count` | Число подтверждённых операций, которых нет на текущем primary |
| `confirmed_missing_sequences` | Идентификаторы этих отсутствующих операций |
| `unconfirmed` | Попытки без успешного ответа; это не счётчик потерянных подтверждённых записей |
| `unconfirmed_present_count` | Подтверждение не получено, но операция найдена в БД |
| `unconfirmed_absent_count` | Подтверждение не получено, операция не найдена в БД |
| `max_success_gap_s` | Максимальный интервал между соседними успешными подтверждениями |
| `error_windows` | Группы неуспешных попыток и момент возобновления подтверждений |

Внутри восстановленного окна `success_gap_s` — время между последним ACK перед ошибками
и первым ACK после восстановления. `failure_to_success_s` отсчитывается от начала
первой неуспешной попытки. Если клиент остановлен до восстановления, окно имеет
`recovered=false`, а `observed_until_finish_s` показывает уже наблюдавшуюся
длительность проблемы. При недостатке успешных операций интервал может быть
`null`; это не нулевая длительность отказа.

Измеряем поведение клиента, включая запуск `psql`, интервал между попытками,
сетевые таймауты и HAProxy. Это не точное время выборов Patroni и не тест
максимальной производительности PostgreSQL. RTO и RPO — заранее заданные цели
восстановления; здесь фиксируем фактические интервалы и отсутствующие
подтверждённые идентификаторы.

После успешного ответа БД клиент ещё должен записать ACK в свой журнал.
Аварийное завершение клиента в этом промежутке может оставить результат
неподтверждённым в журнале. Поэтому измерение требует завершённого файла.

## 12. Поведение приложения: повтор без дубликатов

В предыдущей главе клиент после ошибки переходил к следующему `seq`.
Мы измеряли результаты попыток. Приложению часто нужно закончить именно
исходную операцию — например, создать один заказ, несмотря на несколько
попыток подключения и отправки SQL.

### Что происходит при потере ответа

Есть два разных результата с одинаковым симптомом для клиента:

- PostgreSQL не сохранил операцию, успешного ответа нет.
- PostgreSQL сохранил операцию, но соединение оборвалось до получения ответа.

Безусловный повтор обычного INSERT может создать второй заказ во втором случае.
Клиенту нужен постоянный идентификатор **логической операции**, который остаётся
одинаковым при каждом её повторе. Это ключ идемпотентности: повтор той же
операции с тем же ключом даёт тот же эффект в БД.

### Создаём таблицу с ключом операции

Проверь, что кластер работает. `NODE` может указывать на любой работающий узел:
SQL-клиент подключается к primary через HAProxy.

```bash
make status
make sql
```

```sql
CREATE TABLE IF NOT EXISTS lab_requests (
    request_id uuid PRIMARY KEY,
    body text NOT NULL,
    created_at timestamptz NOT NULL DEFAULT now()
);
```

`request_id` задаётся приложением до первой отправки и сохраняется для повторов.
В упражнении используем фиксированный UUID, чтобы его можно было повторно
скопировать. Ограничение PRIMARY KEY проверяет уникальность на стороне PostgreSQL,
в том числе при конкурентных запросах.

### Отправляем одну операцию дважды

Выполни следующий запрос два раза с тем же UUID и тем же `body`:

```sql
INSERT INTO lab_requests (request_id, body)
VALUES ('11111111-1111-4111-8111-111111111111', 'Учебный заказ')
ON CONFLICT (request_id) DO NOTHING
RETURNING *;
```

В первый раз ожидай одну строку и `INSERT 0 1`. Во второй — пустой RETURNING
и `INSERT 0 0`: конфликт уникального ключа обработан без вставки дубликата.
Если уже выполнял этот пример, строка может существовать с первого запроса.

```sql
SELECT count(*)
FROM lab_requests
WHERE request_id = '11111111-1111-4111-8111-111111111111';

SELECT *
FROM lab_requests
WHERE request_id = '11111111-1111-4111-8111-111111111111';
```

Ожидай `count = 1`. Разные операции должны иметь разные ключи, а повтор одной
операции сохраняет прежний ключ. Если при повторе генерировать новый UUID,
PostgreSQL увидит новую операцию и сможет вставить ещё одну строку.

### Что должен делать клиент при повторе

`DO NOTHING RETURNING` не возвращает существующую строку. После успешного
завершения такой попытки клиент отдельным SELECT читает результат по
`request_id`, проверяет совпадение `body` и возвращает сохранённый результат.
Один ключ с другими данными должен считаться конфликтом, а не новой операцией.

Для обработчика с несколькими изменениями ключ операции и все изменения БД
нужно фиксировать в одной транзакции. Отдельные внешние действия, например
отправка письма или платёж во внешнем сервисе, требуют собственного согласования;
уникальный ключ строки сам по себе их не дедуплицирует.

При сетевой ошибке клиент открывает новое соединение через HAProxy и повторяет
ту же операцию с тем же ключом. Число попыток или общее время ограничивается,
между попытками нужна пауза. Ошибки данных и прав доступа не исправляются
бесконечным повтором. Ниже проверим такое поведение практическим клиентом.

Идемпотентность ограничивает дубликаты в сохранённой истории БД. Сохранность
самой истории зависит от репликации и восстановления; этот ключ не заменяет
синхронную репликацию или резервные копии.

### Практический клиент с переподключением и ограниченными повторами

`request_client.py` завершает одну логическую операцию. Как и клиент нагрузки,
он работает на хосте, использует Python и установленный `psql`, читает пароль
из `.env` и подключается к primary через HAProxy. Таблица `public.lab_requests`
должна быть создана SQL-командой из начала этой главы.

Передай UUID явно: он остаётся тем же при всех внутренних повторах и при
повторном запуске программы. Выполни эту команду дважды:

```bash
python3 request_client.py 22222222-2222-4222-8222-222222222222 --body 'Заказ через клиент'
```

В обоих случаях ожидай `status: confirmed`, одну и ту же строку `request`
и одинаковый `created_at`. Счётчик `attempts` относится к текущему запуску
клиента. Подтверждение означает, что клиент получил результат записи и сверил
его с исходной операцией; оно не обещает сохранность истории при любом отказе.

Каждая попытка открывает новое соединение. В нём `INSERT ... ON CONFLICT DO
NOTHING` фиксируется, затем отдельный `SELECT` читает строку с новым снимком
данных. Это важно и при конкурентных запросах с тем же UUID. Клиент сверяет
`request_id` и `body`, возвращает сохранённое время создания. Содержимое
передаётся через экранируемые переменные `psql`, а не подставляется в SQL
конкатенацией строк. Пример рассчитан на одно изменение строки; несколько
связанных изменений потребуют общей транзакции.

Проверь конфликт данных:

```bash
python3 request_client.py 22222222-2222-4222-8222-222222222222 --body 'Другой заказ'
```

Ожидай ошибку `request_id_conflict` и ненулевой код выхода. Ранее сохранённое
содержимое не изменится. Ошибку нельзя исправить повтором с тем же неверным
содержимым: для новой операции нужен новый ключ.

По умолчанию пределы — 30 попыток, общее время 45 секунд, пауза 1 секунда.
Отдельный вызов `psql` ограничен шестью секундами или оставшимся общим временем,
если его меньше; также действуют таймауты подключения, SQL и ожидания блокировок.
Пределы можно задать явно:

```bash
python3 request_client.py 22222222-2222-4222-8222-222222222222 --body 'Заказ через клиент' --max-attempts 30 --deadline 45 --retry-delay 1
```

Транспортные ошибки, таймауты, временная недоступность primary, deadlock и
ошибка сериализации приводят к повтору. Для серверных ошибок используется
SQLSTATE; ошибки SQL, прав доступа и данных завершают программу сразу.
`psql` не предоставляет SQLSTATE начальных ошибок подключения через libpq:
клиент отдельно различает отказ сервера и временный запуск/остановку по
диагностике в локали C. Это ограничение учебного клиента на `psql`.

При исчерпании лимитов клиент сообщает `not confirmed` и завершается с ошибкой.
Это не означает, что строки нет: запись могла сохраниться до потери ответа.
Повторный запуск с тем же UUID и исходным `body` позволяет получить результат.
Ключ и содержимое должны переживать перезапуск приложения; здесь их сохраняет
пользователь в команде, автоматического дискового журнала операций у клиента нет.

### Проверяем переподключение во время выбора лидера

Сначала дождись здорового кластера с синхронной репликой:

```bash
make status NODE=pg1
```

В примере лидер — `pg2`. Если лидер другой, замени имя только в командах
остановки и возврата узла. Подготовь команду с новым ключом, останови лидера
и сразу запусти клиент:

```bash
docker compose kill -s SIGKILL pg2
python3 request_client.py 33333333-3333-4333-8333-333333333333 --body 'Заказ во время отказа' --deadline 60 --max-attempts 60
```

Клиент должен показать несколько неуспешных попыток, затем `confirmed` после
появления нового primary. Если выборы уже закончились к моменту запуска,
возможен успех с первой попытки. Если этот UUID уже использовался, программа
получит прежнюю строку — для нового опыта выбери новый UUID.

Повтори ту же команду после восстановления доступности, затем проверь через
`make sql`:

```sql
SELECT request_id, body, created_at
FROM public.lab_requests
WHERE request_id = '33333333-3333-4333-8333-333333333333';

SELECT count(*) FROM public.lab_requests
WHERE request_id = '33333333-3333-4333-8333-333333333333';
\q
```

Ожидай одну строку и `count=1`. Верни остановленный узел:

```bash
docker compose start pg2
make status NODE=pg1
```

Дождись обеих streaming-реплик и `Sync Standby`. Этот опыт проверяет новое
подключение после отказа сервера. Неопределённый результат после уже сохранённой
операции отдельно моделируется в `test_request_client.py`: первая попытка
сохраняет строку и теряет ответ, вторая возвращает прежний результат.

Механизмы клиента: [переменные psql и SQL Interpolation](https://www.postgresql.org/docs/17/app-psql.html#APP-PSQL-INTERPOLATION),
[коды ошибок PostgreSQL](https://www.postgresql.org/docs/17/errcodes-appendix.html).

## 13. Обслуживание: настройки и последовательный перезапуск

Теперь меняем конфигурацию работающего кластера. Сначала применим параметр
без перезапуска, затем увидим `Pending restart` и перезапустим PostgreSQL
по одному узлу с плановой передачей лидерства.

### Где менять настройки

| Источник | Для чего используется в этом стенде |
| --- | --- |
| `bootstrap.dcs` в `patroni.yaml` | Начальная общая конфигурация при создании кластера |
| `patronictl edit-config` | Изменение общей конфигурации уже работающего кластера в etcd |
| Локальный `patroni.yaml` и переменные окружения | Настройки конкретного процесса Patroni, например адреса узла |

`show-config` показывает желаемую общую конфигурацию. Фактические значения
на конкретном PostgreSQL смотри через `SHOW` или `pg_settings`.

В Dockerfile файл `patroni.yaml` копируется внутрь образа. Правка файла на хосте
не меняет его в существующем контейнере. Меняем параметры через DCS, поэтому
пересборка образа не требуется.

### Смотрим исходное состояние

```bash
make status
make ctl ARGS="show-config"
make sql
```

```sql
SELECT name, setting, unit, context, pending_restart
FROM pg_settings
WHERE name IN ('log_min_duration_statement', 'shared_buffers')
ORDER BY name;

SELECT pg_postmaster_start_time();
\q
```

Для исходного стенда ожидай:

| Параметр | `setting` | `unit` | `context` | `pending_restart` |
| --- | --- | --- | --- | --- |
| `log_min_duration_statement` | `-1` | `ms` | `superuser` | `f` |
| `shared_buffers` | `8192` | `8kB` | `postmaster` | `f` |

`-1` отключает журналирование по длительности. `8192` блоков по `8kB` — это
64 MiB; `SHOW shared_buffers` покажет `64MB`. Контекст `postmaster` означает,
что новое значение вступает в силу только после запуска PostgreSQL.
Запомни время запуска: оно поможет отличить reload от restart.
Если значения отличаются, сохрани свои исходные значения для возможного отката.

### Меняем параметр без перезапуска

В терминале:

```bash
make ctl ARGS="edit-config --set postgresql.parameters.log_min_duration_statement=1000"
```

Patroni сам обнаружит обновление DCS и применит параметр;
при `loop_wait=5` дай ему несколько секунд. Открой новое SQL-соединение:

```bash
make sql
```

```sql
SHOW log_min_duration_statement;
SELECT pg_postmaster_start_time();
SELECT pg_sleep(1.2);
\q
```

Ожидай `1s`, прежнее время запуска PostgreSQL и отсутствие `Pending restart`.
Запрос с `pg_sleep` превысил порог в 1000 мс. Для исходного лидера `pg3`:

```bash
docker compose logs --since=2m pg3
```

Найди запись с длительностью запроса и `SELECT pg_sleep(1.2)`.
Если лидер другой, смотри его логи. Здесь длительность намеренно создана
ожиданием.

`patronictl reload` перечитывает локальный конфиг Patroni и посылает PostgreSQL
сигнал перечитать его конфигурацию. Для только что изменённого DCS он обычно
не нужен. Чтобы отдельно попробовать reload на одном узле:

```bash
make ctl ARGS="reload 'how to drive ;)' pg3"
```

После обработки reload время `pg_postmaster_start_time()` остаётся прежним.

### Получаем Pending restart

Увеличим `shared_buffers` с `64MB` до `80MB`:

```bash
make ctl ARGS="edit-config --set postgresql.parameters.shared_buffers=80MB"
make ctl ARGS="show-config"
make status
```

Подтверди изменение и повторяй `make status`, пока у узлов не появится
`Pending restart`. DCS уже содержит `80MB`, но работающие процессы ещё
используют `64MB`. На primary через `make sql`:

```sql
SHOW shared_buffers;
SELECT name, setting, unit, context, pending_restart
FROM pg_settings
WHERE name = 'shared_buffers';
\q
```

Ожидай `64MB` и `pending_restart=t`. Reload не применит этот параметр:
ему нужен restart PostgreSQL.

### Перезапускаем реплики по одной

Для команд ниже исходное состояние: лидер `pg3`, реплики `pg1` и `pg2`.
Если роли другие, сначала согласуй имена с `make status`.
Начнём с асинхронной реплики `pg2`:

```bash
make ctl NODE=pg1 ARGS="restart 'how to drive ;)' pg2 --pending"
make status NODE=pg1
```

В интерактивных вопросах выбери немедленный перезапуск (`now`), не задавай
условие по версии PostgreSQL и подтверди операцию. `--pending` выбирает узел
только при наличии признака ожидающего перезапуска.
Дождись `streaming` у `pg2` и исчезновения её `Pending restart`.
Проверь именно эту реплику, подключившись локально внутри её контейнера:

```bash
docker compose exec pg2 psql -X -U postgres -d postgres -c "SHOW shared_buffers;"
```

Ожидай `80MB`. Затем отдельно перезапусти `pg1`:

```bash
make ctl NODE=pg2 ARGS="restart 'how to drive ;)' pg1 --pending"
make status NODE=pg2
```

Дождись обеих streaming-реплик и назначения `Sync Standby`. При перезапуске
синхронной реплики запись может ждать её замены; в текущем нестрогом режиме
Patroni также может временно продолжить запись без синхронной реплики.
Проверяй фактические роли после каждого шага.

### Передаём лидерство и обслуживаем бывший primary

Теперь обе реплики должны использовать `80MB`, а `pg3` ещё может ожидать
перезапуска. Выбери в `make status` текущий `Sync Standby` для switchover.
Если это `pg1`, команда такая; если `pg2` — замени кандидата:

```bash
make ctl NODE=pg1 ARGS="switchover --leader pg3 --candidate pg1"
make status NODE=pg1
```

Подтверди переключение. Дождись нового лидера, возврата `pg3` в `streaming`
и здоровой синхронной репликации. Проверь `SHOW shared_buffers` локально на
`pg3`: при смене роли PostgreSQL мог уже перезапуститься и применить `80MB`.
Если `Pending restart` сохранился, перезапусти бывшего лидера как реплику:

```bash
make ctl NODE=pg1 ARGS="restart 'how to drive ;)' pg3 --pending"
make status NODE=pg1
```

Если признак уже исчез, дополнительный restart не требуется.
Switchover разрывает существующие клиентские соединения; новые подключения
через прежний адрес HAProxy попадут на нового лидера после обновления проверок.

### Проверяем результат и убираем учебное логирование

На каждом из `pg1`, `pg2`, `pg3` выполни прямую проверку, меняя имя контейнера:

```bash
docker compose exec pg1 psql -X -U postgres -d postgres -c "SELECT name, setting, unit, pending_restart FROM pg_settings WHERE name='shared_buffers';"
docker compose exec pg1 psql -X -U postgres -d postgres -c "SHOW shared_buffers;"
```

На всех трёх ожидай `setting=10240`, `unit=8kB`, `pending_restart=f` — это
`80MB`. Через `make sql` проверь доступность таблиц `notes` и `lab_requests`.

Затем убери включённое логирование медленных запросов:

```bash
make ctl ARGS="edit-config --set postgresql.parameters.log_min_duration_statement=null"
```

Если настройка была задана раньше, верни сохранённое значение вместо `null`.
После применения проверь его через `SHOW log_min_duration_statement`.
`shared_buffers=80MB` оставляем как результат упражнения. Для возврата к
`64MB` нужна такая же процедура изменения DCS и последовательного применения.

Основа упражнения: [конфигурация Patroni](https://patroni.readthedocs.io/en/latest/patroni_configuration.html),
[reload](https://patroni.readthedocs.io/en/latest/patronictl.html#patronictl-reload),
[restart](https://patroni.readthedocs.io/en/latest/patronictl.html#patronictl-restart),
[pg_settings](https://www.postgresql.org/docs/17/view-pg-settings.html).

## 14. Pause/resume: режим обслуживания

`pause` временно приостанавливает автоматическое управление PostgreSQL со
стороны Patroni, в том числе автоматический failover. Такой режим нужен для
работ, при которых оператор сам управляет состоянием PostgreSQL, например
при отдельных процедурах обновления основной версии или восстановления.

Работающие PostgreSQL продолжают обслуживать запросы и передавать WAL.
Patroni продолжает публиковать состояние узлов в DCS, а работающий лидер —
продлевать свою блокировку. Некоторые ручные операции через `patronictl`
остаются доступны; pause не запрещает оператору переключать роли вручную.

Если primary остановится в этом режиме, автоматического повышения реплики
не будет. Поэтому упражнение выполняем на здоровом кластере и заканчиваем
командой `resume`.

### Фиксируем исходное состояние

```bash
make status NODE=pg1
make ctl NODE=pg1 ARGS="show-config"
make sql NODE=pg1
```

```sql
SELECT pg_is_in_recovery(), pg_postmaster_start_time();
\q
```

Ожидай один лидер, две streaming-реплики и `Sync Standby` в нашем синхронном
режиме. В конфигурации `pause` должен отсутствовать или быть `false`.
Запомни лидера, timeline и время запуска PostgreSQL.

### Приостанавливаем автоматическое управление

```bash
make ctl NODE=pg1 ARGS="pause --wait"
make status NODE=pg1
make ctl NODE=pg1 ARGS="show-config"
```

`--wait` ждёт, пока все узлы увидят режим обслуживания. Ожидай сообщение
об успешной приостановке, пометку `Maintenance mode: on` в статусе и
`pause: true` в общей конфигурации. Само включение pause не меняет лидера
и не перезапускает PostgreSQL.

### Проверяем запросы и репликацию

Создай отдельную учебную операцию через HAProxy:

```bash
python3 request_client.py 44444444-4444-4444-8444-444444444444 --body 'Запись в режиме pause'
```

Ожидай `confirmed`. Повторный запуск с этим UUID вернёт ту же строку.
Через `make sql NODE=pg1` проверь время запуска и состояние отправителей WAL:

```sql
SELECT pg_is_in_recovery(), pg_postmaster_start_time();
SELECT application_name, state, sync_state
FROM pg_stat_replication
ORDER BY application_name;
\q
```

Ожидай `pg_is_in_recovery()=f`, прежнее время запуска и две streaming-реплики.
Если лидер — `pg1`, проверь доставку строки непосредственно на реплике `pg2`:

```bash
docker compose exec pg2 psql -X -U postgres -d postgres -c "SELECT request_id, body FROM public.lab_requests WHERE request_id='44444444-4444-4444-8444-444444444444';"
```

Если `pg2` сейчас лидер, выбери другую работающую реплику. Дождись появления
строки. Отдельно останавливать узлы для этой проверки не требуется.

### Возвращаем автоматическое управление

```bash
make ctl NODE=pg1 ARGS="resume --wait"
make status NODE=pg1
make ctl NODE=pg1 ARGS="show-config"
```

Ожидай сообщение об успешном возобновлении управления. Пометка обслуживания
должна исчезнуть, `pause` — отсутствовать или быть `false`. Проверь наличие
одного лидера, двух streaming-реплик и `Sync Standby`.

Основа упражнения: [Pause/Resume в Patroni](https://patroni.readthedocs.io/en/latest/pause.html),
[patronictl pause](https://patroni.readthedocs.io/en/latest/patronictl.html#patronictl-pause),
[patronictl resume](https://patroni.readthedocs.io/en/latest/patronictl.html#patronictl-resume).

## 15. Диагностика: от симптома к причине

Цель — сопоставить состояние контейнеров, координации, PostgreSQL и клиентского
подключения. Диагностику выполняем после `resume` на здоровом кластере, чтобы
сначала увидеть нормальные результаты. Для HTTP-команд нужен `curl` на хосте.

### Контейнеры и роли

```bash
docker compose ps --all
make status NODE=pg1
make ctl NODE=pg1 ARGS="show-config"
```

Ожидай семь работающих контейнеров, один лидер, две streaming-реплики и
`Sync Standby` при синхронном режиме. Проверь отсутствие `pause: true` и
`Pending restart`. Состояние `healthy` зависит от конкретного healthcheck:
например, у HAProxy он проверяет синтаксис конфигурации. Подключение к БД
через HAProxy проверяется отдельно ниже.

### HTTP-проверки, которые использует HAProxy

В текущем примере лидер — `pg1`. Проверь `/primary` каждого узла:

```bash
curl -sS --max-time 3 -o /dev/null -w 'pg1 /primary: %{http_code}\n' http://127.0.0.1:8001/primary
curl -sS --max-time 3 -o /dev/null -w 'pg2 /primary: %{http_code}\n' http://127.0.0.1:8002/primary
curl -sS --max-time 3 -o /dev/null -w 'pg3 /primary: %{http_code}\n' http://127.0.0.1:8003/primary
```

Ожидай `200`, `503`, `503`. На здоровой реплике `503` для `/primary` означает,
что она не подходит для записи через этот endpoint. Сравни проверки `pg2` и `pg3`:

```bash
curl -sS --max-time 3 -o /dev/null -w 'pg2 /health: %{http_code}\n' http://127.0.0.1:8002/health
curl -sS --max-time 3 -o /dev/null -w 'pg2 /replica: %{http_code}\n' http://127.0.0.1:8002/replica
curl -sS --max-time 3 -o /dev/null -w 'pg3 /health: %{http_code}\n' http://127.0.0.1:8003/health
curl -sS --max-time 3 -o /dev/null -w 'pg3 /replica: %{http_code}\n' http://127.0.0.1:8003/replica
```

Оба ответа должны быть `200`. `/health` проверяет работающий PostgreSQL,
`/primary` — primary с блокировкой лидера, `/replica` — подходящую для чтения
реплику с учётом её тега `noloadbalance`. Порт `8001` относится к `pg1`,
`8002` — к `pg2`, `8003` — к `pg3`, независимо от их ролей.

### Здоровье etcd

Проверяй все три endpoint, указав их явно:

```bash
docker compose exec etcd1 etcdctl --endpoints=http://etcd1:2379,http://etcd2:2379,http://etcd3:2379 endpoint health --write-out=table
docker compose exec etcd1 etcdctl --endpoints=http://etcd1:2379,http://etcd2:2379,http://etcd3:2379 endpoint status --write-out=table
```

Ожидай три `HEALTH=true`, одного Raft-лидера etcd и пустые поля ошибок.
Лидер etcd и primary PostgreSQL — разные роли в разных системах. При ошибках
DCS смотри также логи etcd и Patroni; `patronictl list` сам зависит от DCS.

### Фактическая репликация PostgreSQL

```bash
make sql NODE=pg1
```

```sql
SELECT pg_is_in_recovery(), inet_server_addr(), inet_server_port();

SHOW synchronous_standby_names;

SELECT application_name, state, sync_state,
       pg_wal_lsn_diff(pg_current_wal_lsn(), replay_lsn) AS replay_lag_bytes
FROM pg_stat_replication
ORDER BY application_name;

SELECT pid, state, wait_event_type, wait_event
FROM pg_stat_activity
WHERE wait_event = 'SyncRep';
\q
```

На primary ожидай `pg_is_in_recovery()=f`, две строки репликации в `streaming`,
одну `sync` и одну `async`. На спокойном здоровом стенде отставание обычно
нулевое; под записью оно может кратковременно расти. Ноль строк для `SyncRep` значит
сейчас нет сессий, ожидающих синхронного подтверждения. Сам синхронный режим включён.
Если запись зависает на нём, проверяй доступность синхронной реплики и
настройки `synchronous_mode_strict`.

### Подключение через HAProxy

Предыдущий SQL шёл через primary-endpoint HAProxy. Теперь подключись к
read-endpoint:

```bash
make sql NODE=pg1 PORT=5001
```

```sql
SELECT pg_is_in_recovery(), inet_server_addr(), inet_server_port();
\q
```

Ожидай `pg_is_in_recovery()=t`. Отдельное подключение может попасть на другую
реплику. `NODE=pg1` определяет контейнер клиента, роль целевой БД выбирает
HAProxy. `inet_server_port()` показывает порт PostgreSQL за HAProxy — `5432`.

### Если результат отличается

| Симптом | Что проверять дальше |
| --- | --- |
| Контейнер остановлен или перезапускается | `docker compose logs --tail=100 pg2` для нужного сервиса |
| Лидера нет | Здоровье etcd, режим pause, доступность допустимых кандидатов, логи Patroni |
| PostgreSQL работает, но `/primary` возвращает 503 | Его роль, блокировку лидера и состояние DCS |
| Прямой SQL к узлу работает, через HAProxy — нет | HTTP-проверки роли, логи HAProxy, доступность портов и сети |
| COMMIT ждёт `SyncRep` | Синхронную реплику и строгость синхронного режима |
| Реплика не догоняет или не запускается | WAL receiver, удержание WAL и сообщения об отсутствующем сегменте; затем упражнение reinit |
| Настройка в DCS отличается от SHOW | `pending_restart`, контекст параметра, локальные и сессионные переопределения |

Для истории переключений:

```bash
make ctl NODE=pg1 ARGS="history"
docker compose logs --since=5m pg1 pg2 pg3 haproxy
```

Основа упражнения: [REST API Patroni](https://patroni.readthedocs.io/en/latest/rest_api.html),
[проверка состояния etcd](https://etcd.io/docs/v3.6/tasks/operator/how-to-check-cluster-status/),
[представления статистики PostgreSQL](https://www.postgresql.org/docs/17/monitoring-stats.html).

## Команды и подключение с хоста

Расшифровка `sql`, `ctl` и параметров `NODE`, `ARGS`, `PORT` —
в разделе [«Как читать команды»](#как-читать-команды).

| Назначение | Адрес |
| --- | --- |
| SQL к primary | `127.0.0.1:55432` |
| SQL к репликам | `127.0.0.1:55433` |
| REST API pg1 / pg2 / pg3 | `127.0.0.1:8001` / `8002` / `8003` |

В DBeaver: пользователь `postgres`, база `postgres`, пароль — значение
`PATRONI_SUPERUSER_PASSWORD` из локального `.env`.
`make sql` подставляет пароль внутри контейнера.

```bash
make ctl ARGS="show-config"       # общая конфигурация из DCS
make ctl ARGS="edit-config"       # изменить её интерактивно
make logs                         # Ctrl+C завершает просмотр логов
make down                         # удалить контейнеры и сеть, сохранить volumes
make up                           # поднять кластер с сохранёнными данными
make acceptance                   # проверка в отдельном временном кластере
make load DURATION=60             # непрерывная запись через HAProxy
make load-report                  # сверка подтверждений с текущим primary
```

`bootstrap.dcs` из `patroni.yaml` применяется только при создании кластера.
Для существующего кластера общую конфигурацию меняй через `edit-config`.
Локальные настройки требуют отдельного reload/restart в зависимости от параметра.

Начать заново, **удалив все учебные данные и состояние etcd**:

```bash
docker compose down --volumes
make up
```

Автопроверка использует уникальное имя Compose-проекта, не публикует порты
и удаляет свои контейнеры и volumes в конце. Она проверяет две streaming-реплики,
маршрутизацию SQL, запрет записи на реплике, switchover, SIGKILL лидера,
возврат бывшего лидера и восстановление после потери кворума etcd.
При потере кворума проверяются ответы REST API, прямое состояние PostgreSQL
на всех узлах (реплика либо остановлен) и отказ записи через HAProxy.
Перед отказом тест ждёт доставки контрольной строки на все узлы.
Это проверка конкретного сценария, а не гарантия отсутствия потерь в async-режиме.

## Итоговая проверка

```bash
make check
make acceptance
```

`make check` проверяет расчёт отчёта нагрузки и поведение клиента при повторах,
неопределённом результате и исчерпании лимитов. Автопроверка `make acceptance`
покрывает базовый асинхронный сценарий.

Успешный итог acceptance: `PASS: replication, routing, switchover, failover,
rejoin, etcd quorum.` Временный кластер должен удалиться после прогона;
основной стенд и его учебные данные сохраняются. Журналы измерений сохраняются
отдельно в `.local/workload/`.
